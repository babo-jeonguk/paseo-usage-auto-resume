# Behavior, data access and troubleshooting

[English README](../README.md) · [한국어 README](../README.ko.md)

## From a limit stop to a resume

Usage Auto Resume detects short provider limit notices and explicit limit error codes at the end of a turn. Claude can finish a turn normally while leaving a limit notice, so detection also checks the closing assistant message. Context overflow, ordinary errors and API billing failures are excluded.

At the end of a turn that was not canceled, the plugin reads the agent's latest 20 timeline items and checks those after the latest user message; the timeline Paseo 0.11 and 0.12 sent with a turn's end is not used. When they cannot be read, the failure is logged and only the error the turn failed with is checked.

Each daemon runs its own copy of the plugin, and a turn's end reaches only the daemon that runs the agent. An agent that Paseo's connected hosts run on another machine is resumed only when the plugin is installed and turned on in that machine's daemon.

The plugin keeps one resume reservation per agent. When a notice states a reset time, it schedules that time plus two minutes without querying usage. Codex and Claude authentication is checked separately to bind the account/model when available; a failed identity check does not replace the stated schedule with an earlier verification wait. API-key and external billing routes are excluded. A saved OAuth login alone does not override an active API route.

The route is the one the CLI actually uses. Where a CLI reports which authentication it uses and the report can tell the routes apart, that report decides, following the CLI's own precedence: an API key the CLI prefers over an automation token is API billing, and an automation token the CLI prefers over a saved login is what gets checked, never the saved login. An environment variable alone excludes a route only when the report cannot show it: a route override such as a base URL, which sends requests elsewhere whatever the credential, or a credential the report cannot tell apart from a subscription one. A CLI without such a report keeps variable checks. The variables that still exclude a route before any probe are `OPENAI_BASE_URL` for Codex; `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL` for Claude; `GEMINI_API_KEY`, `AGY_ADC_AUTH` and `GOOGLE_GEMINI_BASE_URL` for Antigravity. OpenCode is classified by the selected model's provider. When a report cannot be obtained, the reservation waits for verification, and a later check that obtains a report of API billing cancels it.

Automation tokens (`CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`, and `CODEX_ACCESS_TOKEN` or a token persisted by `codex login --with-access-token`) draw on the subscription and are resumed. Probes need the token's value: the one captured when the agent's session opened is kept in memory only. Reservations store a one-way fingerprint of each token instead. After a restart, or for a reservation made before its session was seen, a token from the daemon environment or provider configuration is used only when its fingerprint matches the saved one; otherwise the route waits for account verification. A reservation saved by an older version has no fingerprint, so its token is treated as unavailable.

Without a reset time, Codex and Claude authentication and account/model usage are checked directly to choose the schedule, including for workspace credit notices. OpenCode follows the billing route its model selects, as described below. Failed authentication or usage checks create a verification wait. Every Codex and Claude delivery still requires fresh subscription authentication and available usage, except a Claude setup token that cannot read usage, described below; every OpenCode Go delivery requires fresh usage. A timestamp alone never authorizes a continue.

- **Codex:** reads account, config and auth-method status from Codex's app-server, the same one Paseo runs Codex agents on, without refreshing the login. The auth method decides the route: an API key is API billing; a ChatGPT login and an access token are subscriptions; no method, or one Codex will not report, waits for verification. `CODEX_API_KEY` excludes nothing, because that app-server ignores it; an API key Codex actually uses, such as one saved by its login, is reported as one. A non-OpenAI model provider or a provider override is API billing.
  - **ChatGPT login:** when usage is needed, it queries the exact ChatGPT workspace's usage. Account/workspace and model scope are bound to the reservation. The login is read from the home Codex reports for itself; a Codex that reports none falls back to `CODEX_HOME`, then `.codex` in the user profile on Windows or in `HOME` elsewhere.
  - **Access token** (a personal access token or a legacy agent-identity token, from the environment or persisted): Codex reads the rate limits in the same app-server session and attaches the token itself; no login file is read and no token reaches the plugin's own requests. The account must be a ChatGPT account with a plan. The backend's explicit usage permission decides when it gives one; otherwise the stopped model's bucket, else the `codex` bucket, has its five-hour and weekly windows judged like a ChatGPT login's. No usable window, a refused request, a missing workspace or user, or a workspace other than the one Codex routes to waits for usage verification. The workspace and user, not the token, are bound to the reservation with the model, so rotating a token for the same seat keeps it and another user cancels it.
- **Claude:** checks `auth status --json`, whose authentication method decides the route. An API key, a cloud provider (Bedrock, Vertex or Foundry, judged as Claude judges the switch's value, so `0` or `false` stays off) or any other method is API billing; not logged in or unreadable waits for verification. `ANTHROPIC_AUTH_TOKEN` is excluded before the check because the report shows it as a setup token, and `ANTHROPIC_BASE_URL` because the report omits it.
  - **Setup token** (`oauth_token`): only the token's own value is checked, against the OAuth profile, and no other request is made. A token whose scope may not read the profile (`oauth_scope_insufficient`) is valid but cannot read usage, so its reservation follows the notice like Antigravity's: a stated reset schedules that reset, no reset gives the bounded 15/30/60-minute continues, delivery sends without a usage check, and **Resume now** sends. The token's fingerprint and the model are bound to the reservation, so replacing the token cancels it. A token that can read the profile is verified like a claude.ai login below, account and organization coming from the profile alone. A revoked or invalid token, any other answer or a network failure waits for account verification, also at due time.
  - **claude.ai login:** verifies the OAuth profile against the account and organization `auth status` reports. When usage is needed, it reads subscription usage. Account/organization and model scope are bound to the reservation. On macOS it reads the selected profile's Keychain item, with a two-second timeout per lookup, then its same-profile `.credentials.json` fallback if the item is unavailable. `CLAUDE_CONFIG_DIR` selects separate stores; the CLI's `CLAUDE_SECURESTORAGE_CONFIG_DIR` override, including an empty value selecting the default store, is also honored. Without either override, the credential file is the one in the configuration directory `auth status` reports, else `.claude` in the user profile on Windows or in `HOME` elsewhere. It never searches another profile to find a working token. Missing, unreadable or expired credentials wait for verification.
- **Antigravity:** agy 1.1.12 or later can supply model quota through a separate read-only print-mode `/usage` command. A notice with a reset still schedules that reset without probing; without one, and before every delivery including **Resume now**, applicable quota windows are checked. `gemini-4-argon-*` uses `gemini-argon-*` buckets, other `gemini-*` models use the remaining `gemini-*` buckets, and `claude-*`/`gpt-oss-*` use `3p-*` buckets. Missing Argon buckets are not inferred from shared Gemini quota. Buckets the model does not use, or whose remaining fraction is unreadable, are skipped; a model left without a readable bucket uses the fallback. A remaining fraction of zero or below is exhausted. There is no account identity binding. Known API routes (`GEMINI_API_KEY`, `AGY_ADC_AUTH`, `GOOGLE_GEMINI_BASE_URL`) are excluded before any probe; when the provider configuration cannot be read to check them, the reservation waits for verification as for Codex and Claude. An unsupported version/launcher, failed probe or unmapped model preserves the previous behavior: follow the stated reset, otherwise use the bounded retry sequence, and allow **Resume now**. Antigravity's replayed historical errors are not detected or suppressed.
- **OpenCode:** the plugin does not check OpenCode's version. It requires the agent's own session to be in OpenCode 2's session store in OpenCode's database; the plugin never reads OpenCode 1's own storage, and a session migrated into OpenCode 2 is judged by the records OpenCode 2 now writes for it. A server reached on another host through `PASEO_OPENCODE_SERVER_URL`, or one using another data directory, is not trusted and waits for verification. An unreadable database waits too. The billing route comes from the agent's model: `opencode-go/…` is OpenCode Go; `opencode/…` is OpenCode's own models, where only a recorded free-usage limit is resumed; a model of any other provider run through OpenCode is excluded like an API route. For Go, the selected `opencode-go` key credential is read read-only from OpenCode's database (`$XDG_DATA_HOME/opencode/opencode.db`, else `~/.local/share/opencode/opencode.db`), and the Go usage endpoint's rolling, weekly and monthly windows decide, with a window reported rate-limited or at 100% used up; the selected credential and its key, plus the model, are bound to the reservation, so replacing the key or the selected credential cancels it like an account change. For free models, the agent's own OpenCode session's latest finished-turn record is read, and only a record whose type states its meaning is acted on: a `provider.free-limit` record that carries the retry delay OpenCode stored with it (written by OpenCode 2.1.2 and later) waits until the recorded failure time plus that delay, without any usage call or account binding, and without a usable delay it uses the bounded 15/30/60-minute retries. A free limit older OpenCode recorded as a generic quota failure is excluded like API billing; a recorded balance, budget or credit failure is excluded the same way; a failure recorded without an error waits for verification.

For Codex and Claude, the applicable five-hour and weekly usage windows determine the wait when the notice has no reset and during pre-send checks; for Antigravity, when its quota can be read, the buckets mapped to the model above do; for OpenCode Go, its rolling, weekly and monthly windows do, while free OpenCode models use the reset recorded with the free-limit failure. Multiple exhausted windows wait for their latest known reset. Codex's exact-model `model_usage.available_at` can supply that model's reset. A known reset gets a two-minute buffer; a stale exhausted window still requires fresh confirmation of recovery after that timestamp passes.

Credit and spending notices are also treated as limit stops. They do not themselves decide readiness: credits indicate whether usage can run past a window. When no applicable window is exhausted and usage is verified ready, the plugin retries the continue after 15, 30 and 60 minutes, then gives up if each hits another limit. A future reset in the notice is still honored. An exhausted window discovered later starts this retry sequence over. Refilling credits does not restart a finished sequence.

For Codex and Claude, unknown authentication or unavailable usage schedules a read-only recheck in 15 minutes, without a continue. A Claude setup token that cannot read usage follows the notice and the bounded retries instead, as described above. A confirmed exhausted window without a usable future reset does the same for every supported provider. For limit reservations, Antigravity falls back to the bounded 15/30/60-minute continue sequence when its quota cannot be read and no reset is stated. Actual continues share a bound of 24 consecutive limit/overload stops; read-only checks do not consume these attempts.

## Checks before sending

Every hook, tick and **Resume now** follows the table below. Each reservation has an id it keeps while it is moved, postponed, switched, noted or planned again; one that replaces it gets another. Which reservation a change applies to depends on where it comes from. A turn event acts on the reservation it saw, wherever it has moved meanwhile, never on one that replaced it. A user's change acts on the reservation the screen showed, as described under extra instructions below. A due-time attempt, at the tick or from **Resume now**, acts only on the row it checked, whatever it finds, so a reservation moved meanwhile is checked again at its new time. Archiving the agent, turning its provider off in settings, turning Labs off (for an overload reservation) and a stop that finds API billing act on whatever pending reservation the agent has then. A *pending* reservation has not been sent yet; a *sent* one is the record kept after its continue until a turn finishes. A continue still being sent keeps its claim until the send ends, whatever else happens: only a detected limit or enabled overload stop replaces it with a new reservation, or ends it when it gives up, and a restart drops it. A *new message* is one the user sent after the reservation was made, by Paseo's `lastUserMessageAt`. A Claude subagent's notification starts a turn without one.

**Turn events.** A new message cancels a pending reservation first, whatever the event and whether or not a new reservation can be planned; a turn that stops at a limit or enabled overload then gets a reservation of its own. The agent must be read to see a message: if it cannot be, a finished turn is recorded as finished, a stop at a limit or an overload plans nothing, and the due-time check still finds the message. Without a new message:

| Event | Pending reservation | Sent record | None |
|---|---|---|---|
| A turn starts | kept | kept | — |
| A turn finishes | canceled as a finished turn | cleared, unrecorded | — |
| A turn fails without a limit | kept | kept | — |
| A turn is stopped | kept | kept | — |
| A turn stops at a limit | planned again as a limit reservation, below | a new limit reservation, one more continue counted | a new limit reservation |
| A turn ends with a detected provider overload (Labs on) | kept without counting or resampling its time | next overload stage, one more continue counted, or give up at a bound | first overload stage |

A stop at a limit makes no reservation while provider settings cannot be read or the provider is off, and, when the account turns out to use API billing, cancels a pending reservation and clears a sent record. Planning a pending reservation again keeps its switch and extra instructions, and the account and model it is bound to; a stop under another account cancels it. Its reset follows the new notice or usage lookup, and its time follows the new plan, except that a time the user chose stays while it is later. It counts no continue, since none was sent: a retry plan keeps the retry sequence where it was, or enters it at its first step, and any other plan leaves it.

**At the due time**, an overload reservation first cancels if Labs is off, and waits for the next check while the resume settings cannot be read. Then checks run in this order:

1. Provider settings cannot be read: wait for the next check.
2. The provider is off, or no longer runs a supported CLI: cancel.
3. The agent is gone or archived, or its provider or model changed: cancel.
4. A new message: cancel.
5. The agent is starting: cancel. A closed agent goes on, and the continue reopens its saved session. Paseo closes an agent's runtime when, for example, the daemon stops or crashes, even mid-turn, or, by default from 0.14, the agent has been idle for an hour. A continue whose reopen fails is recorded as could not be sent.
6. The agent awaits permission or input: cancel.
7. The agent is in a turn: wait for it to end, without a usage lookup. A reservation that is turned off waits too, so the turn's end decides it.
8. The reservation is turned off: skip it.
9. The account uses API billing, or changed: cancel.
10. Confirmed used-up usage converts an overload reservation to a limit reservation, clearing its overload stage even if no reset is known. Unverified usage keeps its kind and stage. Usage is used up or cannot be verified, or the reset stated in the notice is still ahead: move the reservation to when it renews or can be checked again. A time the user chose no longer counts as theirs.
11. The usage lookup takes a few seconds, so read the agent again and repeat checks 3 to 8, then read the provider settings again: unreadable waits, and a provider turned off cancels. For an overload reservation, read Labs again before claiming: unreadable waits, and off cancels.
12. Claim the reservation and send the continue, steering it into a turn that started in between, where the provider supports that. The extra instructions are then removed.

**Resume now** runs the same checks, with four differences. It ignores the reset stated in the notice. It sends a reservation that is turned off. In a turn, it answers that the agent is still working, and when usage holds it, it answers with the reason; both leave the reservation as it was. A check that cancels cancels it as it would at the due time.

A turn that never ends keeps its reservation waiting with no deadline.

A known selected model is saved even when authentication is unavailable. A different model, a change from a previously verified Codex/Claude account identity, or a different OpenCode Go credential or key cancels the reservation, including after a restart. If account identity could not initially be verified, it is bound on the first successful check.

Sending is claimed in persistent storage first to prevent duplicate delivery after a crash. A send interrupted at that point may therefore be lost rather than retried. These checks do not provide an atomic guarantee against every concurrent change between checking and sending; a provider that cannot steer has a turn started in that moment replaced by the continue.

The default continue prompt asks the parent agent to review the latest conversation, workspace and task status, then continue unfinished work. It also asks the parent to resume unfinished subagents using their existing identities and tools, respect user pauses/cancellations and report blockers. The prompt can be replaced under **Continue prompt** in the plugin's settings. Saving it empty, or identical to the default, goes back to the default, which then follows later versions' changes to it. A custom prompt without the subagent instructions changes how subagents continue: the parent may start new subagents, or none, instead of resuming the unfinished ones by their existing IDs. A reservation's extra instructions, when it has them, are added below the prompt under a fixed heading. The prompt is read when the continue is sent, so a change saved while a due reservation is being checked applies to it. The plugin sends only to the parent; actual subagent continuation depends on the tools available to it. It does not create a new agent or switch providers.

## Labs: retry after a provider overload

The `resume.overloadRetry` setting defaults to false. It enables Codex, Claude and Antigravity capacity retries only after a live final turn-end event, after the CLI has finished its own retries. Limit detection always runs first. The startup scan does not detect overloads; persisted overload reservations still survive restart.

Detection is restricted to the provider forms in [the evidence note](research/overload.md): Codex's exact capacity error; Claude Code's own overload classes in its short final `API Error: …` notice (a 529 status, its `Repeated 529 Overloaded errors` give-up, or an `overloaded_error` body), but not its model-specific high-load notice asking to switch models; Antigravity's final 503 error carrying `MODEL_CAPACITY_EXHAUSTED`. A structured `overloaded_error` code for Claude or `MODEL_CAPACITY_EXHAUSTED` code for Antigravity also identifies a failed turn. Claude alone may report the synthetic notice as `completed`; only the last assistant message, with a fixed prefix and at most 300 characters, is read. Canceled turns, ordinary answers, generic 503/UNAVAILABLE, 500/502/504, stream interruptions, policy capacity and Flex capacity are excluded. Billing, context, authentication and permission errors veto overload classification.

Antigravity support assumes upstream F1 (historical error replay) is resolved. There is no output/tool guard: a genuine failure after partial work is eligible. agy reports the most recent error of a conversation as the result of every later turn, even after a successful reply (traced on agy 1.4.8 without Paseo); on the tested agy 1.4.11 a resumed turn that received a successful reply still reported the old capacity 503. With Labs on, each such turn therefore starts or advances an overload chain: a chain ending in give-up is removed, and the next turn's replay starts another at stage 1, so every user turn in that conversation can be followed by three automatic continues. Upstream replay is neither suppressed nor fixed here.

Each stage waits from the failure that reserved it: 3, 10 and 25 minutes, each with ±20% jitter sampled once when that stage is reserved. `overloadStep: 1 | 2 | 3` is the reserved stage, not a count of already sent prompts. After the third retry also ends in an overload, the chain gives up with `overload_retries`. Verification-only waits, duplicate events while pending, time edits and restarts consume no stage and do not resample jitter. Resume now consumes the reserved stage when sent. The overall 24-continue bound is shared with limit retries; switching kinds never resets `attempts`.

An overload event keeps either kind of pending reservation unchanged, unless a new user message cancels it first. A limit event converts a pending overload to a limit reservation, keeping its identity, switch, note and later user-chosen time under the normal replan rules. A limit stop after an overload send also leaves the overload sequence. A subsequent overload starts at stage 1. An overload in between neither advances nor restarts the 15/30/60-minute limit retry sequence. Normal completion ends the chain. A sent record stays until a turn finishes, and Paseo records a continue as a user message, and the plugin does not record which message was its own, so a user's own message is not told from a continue: when a retry's turn is stopped or fails with another error and the user's next turn then ends in an overload, that turn takes the next stage, or gives up if the third retry was already sent. Limit continues are counted toward the 24-continue bound the same way. A fast final failure while `send` is still resolving can replace its `sending` record with the next reservation; completion of that send must not overwrite the replacement.

Planning overload retries checks identity/API billing but does not query usage. Delivery uses the normal fresh authentication, usage, agent and account/model checks. Confirmed exhaustion converts an automatic attempt to a limit reservation; unreadable verification keeps the overload stage and waits. Resume now differs as before: used-up or unverified usage returns the reason and leaves the reservation's time, kind and stage unchanged. Antigravity's existing quota-reader fallback remains in effect.

The overload prompt is fixed, ignores the custom continue prompt, and asks the agent to review existing edits, tool results and subagent progress before resuming unfinished work. The reservation's note is appended and removed after sending. The built-in prompts avoid detector phrases; arbitrary user notes are not rewritten.

Turning Labs off immediately cancels all pending overload reservations, including individually disabled ones, with `overload_off`. Turning it back on does not restore them. The setting is checked again before claiming. A request already claimed for sending is allowed to finish; disabling Labs does not interrupt agent work. Limit reservations are unaffected. Unreadable resume settings are not Labs off. While the switch cannot be read, no overload retry is planned, the switch neither cancels nor sends a pending one (its due time waits, and **Resume now** reports that settings could not be read), and once it reads again the retry continues from its stage. Every other row of the table still applies meanwhile. In particular, an overload check that cannot read the switch or the agent's CLI leaves the turn event Labs off would see, so a Claude overload notice then reads as a finished turn and cancels or clears as one.

Older jobs with no `kind` remain limit reservations, as does a row whose `kind` this version does not recognize; an overload row whose `overloadStep` is unrecognized is sent as usual and gives up at the next overload after that. The history records the kind of the reservation each result ended. On downgrade, older versions strip `kind` and `overloadStep` and treat pending overload rows as ordinary limit reservations: the dedicated three-stage bound and fixed prompt are lost. This is not behavior-preserving rollback.

## Reservation and provider controls

A new reservation starts enabled. Turning it off leaves it visible until its due time; it can be re-enabled before then. At its due time, a disabled reservation is skipped and removed. Sending another message also cancels it.

**+10m** delays a reservation by ten minutes; it is turned off when the new time would fall outside the range below. Selecting its time opens an editor with **Today**, **Tomorrow**, and the reservation's own day when a weekly reset is further away. The earliest allowed time is the later of reset + two minutes and one minute from now; without a known reset it is one minute from now. The latest is seven days and one hour from now. The editor opens on the reservation's own minute and day (today, when that time has passed), and always accepts what it opened with: no error is shown and **Save** is on, even when seconds put its minute before the earliest allowed time. Saving it unchanged only closes the editor: the reservation keeps its exact time, seconds included, stays off if it was off, and nothing is recorded. Any other time is checked against this range, and **Too early** gives the first whole minute at or after the earliest allowed time, which can be saved. The day choices are fixed when the editor opens, so an editor left open past midnight keeps offering and using those same calendar days, and **Tomorrow** chosen before midnight still means that date afterwards; the allowed range is still checked against the current time, so a time on a day that has since passed is refused as **Too early**. Changing to a different time turns the reservation on. Editing a verification wait changes its next check time; it does not authorize a continue.

The **Auto Resume** header counts the agents that will continue, or, when none will, the agents waiting for verification. Below it, **Next at** names the earliest continue and **Next check at** the earliest verification check among reservations that are on. When both exist, both times are shown, the earlier first (**Next check 19:58 · Next at 21:45**); when they fall in the same minute it reads **Next check and resume at**. Reservations that are off add a skipped count. A reservation being sent is counted like any other, by its switch and whether it waits for verification, until it leaves the list. All turned off shows **All turned off** with no time.

The header switch changes only the pending reservations shown on screen. New reservations and ones already being sent are left alone. The list refreshes every 30 seconds, with a refresh button on desktop and pull to refresh on mobile. Times use the viewing device's time zone. The time left until a due time, on the screen, in the composer popover and in the time editor, is rounded up to the minute and shown in minutes (**in 25m**), in hours and minutes under 24 hours (**in 2h 2m**), and from 24 hours on in days and hours, rounded up to the hour (**in 1d 2h**, **in 7d 1h**); a due or overdue time reads **now**. Screen readers hear it in words (**in 7 days 1 hour**).

Conversations with a reservation have an **Auto Resume** composer pill. It shows the reservation time (a **Retry** time for an overload retry), **Resume off**, **Resuming…**, or a **Check** time for verification waits. Selecting it opens a popover on desktop or a sheet on mobile. The reservation time has an edit button for the time editor and **+10m**, **+30m** and **+1h** below it, followed by the same per-reservation switch, the reservation's **extra instructions** and **Resume now**. The delays are added to the reservation's time, not to now, and are turned off when the result would fall outside the editor's range: no earlier than reset + two minutes or one minute from now, and no later than seven days and one hour from now. Off keeps the pill available for re-enabling before the due time; it does not disable future reservations. Changing to a different time turns the reservation on. Sending jobs cannot be edited. Executed, skipped-at-due-time and canceled reservations lose their pill.

A reservation can carry **extra instructions** for its continue, up to 2,000 characters. Add or edit them with the button on its row in **Auto Resume** (at the end of the title line on a phone), or with **Add extra instructions** in the composer popover. Saving them leaves the reservation's time and switch as they are; it does not turn an off reservation on. They belong to the reservation, not its time: a reservation moved or postponed since it was shown still takes them. Once its continue is being sent, or it has run, been canceled or been replaced, the save is refused and the text stays in the editor until it closes. A time change, the switch and **Resume now** are refused when the reservation moved since it was shown, so they always act on the time in view. While extra instructions are being written, no other editor opens: in the list, every row's time editor and every other row's extra instructions button is off, while other rows' **+10m** and switches stay on; in the composer, **Resume now**, the time editor and the delays are off. While a time is being typed, extra instructions cannot be opened. Escape closes the extra instructions editor only when its text, ignoring spaces at either end, is what it opened with; in the time editor it always cancels. Extra instructions are sent once, with the continue, and then deleted. Postponing a reservation, a new plan for one still waiting, a time change and the switch keep them. A reservation that is canceled, skipped or fails to send takes them with it, including when another message cancels it. A limit hit again after the continue makes a new reservation without them. If the continue is sent while they are still being edited, or another reservation replaces this one, the editor closes and unsaved text is lost.

**Resume now** sends the continue right away, after a second press in place. It is meant for a limit lifted before the reset in the notice, for example by a reset credit, and for checking a verification wait without waiting for its next check. It also works on a reservation that is off. Codex and Claude usage is read first: a window still used up blocks the send and reports when it renews, and an account or usage that cannot be verified also blocks it. A Claude setup token that cannot read usage sends after its token is checked. OpenCode Go is checked the same way; a free OpenCode model reads the reset recorded with its free-limit failure. A blocked Resume now leaves the reservation's time and switch unchanged; its due time checks again as usual. A failed safety check cancels the reservation as it would at its due time. It sends the same prompt and extra instructions an automatic continue would. Antigravity also blocks Resume now when its model's quota is confirmed exhausted. When its quota cannot be read, Resume now sends immediately; if the limit still applies, the agent stops again and a new reservation is made. The app waits about 30 seconds for the answer. When the checks take longer, or the request fails, it says Resume now did not finish and refreshes; the daemon may still finish the attempt and send.

**Recent activity**, below the list, shows how reservations ended in the last 24 hours, up to 200 results: continued, could not be sent, skipped while off, canceled with its reason, gave up after the retry bound, or dropped by a restart. Only final results are recorded; time changes, switches and postponements are not. It starts collapsed with a count by kind, refreshes with the list, and opens the conversation when the agent still exists; an archived agent's button is shown but turned off. An agent deleted since keeps the title recorded at the time. Results that Resume now caused are marked **Resume now**.

Rows in **Auto Resume** and **Recent activity** name their provider by its current name in Paseo, read from Paseo's provider list without an account or usage check, so a renamed profile shows its new name on the next refresh. A provider Paseo no longer lists, or a server too old to send the name, shows the plugin's built-in name for Claude, Codex, Antigravity, OpenCode, Claude Main and Antigravity Main, and the provider ID otherwise. A long name is cut short on one line. Reservations and results are still stored and matched by provider ID.

The composer directory refreshes every ten seconds while the client is active and immediately after local schedule actions. Open conversation controls share the sidebar's schedule cache and refresh every ten seconds. Other clients see changes on their next refresh. A failed directory read replaces the displayed time with **Unavailable**; failed reads in the controls disable changes and offer a retry, and keep showing the reservation already loaded. A failed refresh of the **Auto Resume** list keeps the list, marked as possibly out of date, with **Try again**. Placement uses the reservation's agent workspace, including background workspaces, without listing unrelated conversations.

Provider discovery follows each provider's `extends` chain to built-in Claude, Codex, Antigravity or OpenCode. Profiles sharing an account still have separate switches. All supported providers, including newly discovered ones, start on. Turning one off cancels all of its pending reservations, including individually disabled ones. Turning it back on does not restore them; subsequent limit stops can create new reservations. A startup scan can also find a recent stop again.

Settings are per daemon. Hosts upgrading from the earlier one-ID-per-CLI settings start with every provider on. If provider settings cannot be read, automatic resumes wait rather than falling back to defaults. The continue prompt and Labs switch are stored together, separately from provider settings: if they cannot be read, limit reservations use the default prompt, overload retries wait as described under Labs, and the error is logged once, and the settings screen offers **Retry**, and **Reset** when the stored file is not valid; Reset also turns Labs off, which cancels pending overload retries. A settings save that fails changes nothing: a switch keeps its saved value, turning a provider off cancels no reservation until the save succeeds, and the continue prompt in effect stays the last saved one while the typed text stays in the editor. The screen says so in plain words, as a toast and beside the control that failed, never with the raw error, which goes to the client log. When another client changed the settings first, the message offers **Reload**; otherwise using the control again retries. A later successful save or reload clears the message.

## Restarts and missed stops

Reservations survive daemon and plugin restarts. Paseo supplies its plugin API inside lifecycle hooks and RPC requests, so due-job checks wait until one of these connects it after startup. A connected app supplies the API through composer directory polling, as does opening **Auto Resume**. A connected daemon continues checking without keeping the app open; the daemon host must stay running and awake.

The startup scan searches up to 200 idle/error agents active in the preceding 12 hours for missed limit stops. Existing persisted reservations can wait longer, including for weekly resets. Codex, Antigravity and OpenCode recovery checks error notices; Claude also checks notices in its latest 20 timeline items, and an agent whose timeline cannot be read is logged and skipped. A missed stop is scheduled unless the agent already has a reservation that is pending or being sent; after a sent continue it counts as one more automatic continue. Closed agents are not searched, so a stop is missed when the agent was closed before the plugin started again, as every agent is after a daemon restart.

At session open, the plugin captures non-secret launch paths, credential-store selectors, the OS username used for Keychain lookup, Claude's cloud-provider switches, credential-presence flags and automation-token fingerprints. These survive restarts with the reservation. Automation-token values are kept in memory only, as described above. For a session opened before the plugin loaded, account checks use the daemon environment plus provider configuration; environment values added by other plugins at session open are not available. For Codex and Claude, unrecognized quota shapes and custom launchers with multiple command arguments wait for verification. OpenCode waits when its agent session is not in its database or the database is unreadable. Antigravity instead preserves its notice/retry behavior. Known one-command launchers can use native account/status protocols. Because the plugin reads session opens, Paseo 0.14 and later reopen the session of each open agent before its next prompt whenever the plugin starts, stops or reloads, including on install and update. A continue whose reopen fails is recorded as could not be sent.

## Data access and storage

The plugin reads agent state, recent timeline notices, provider configuration and configured launch environments through Paseo. It reads CLI login stores and runs read-only status probes to identify the authentication actually in use.

Codex checks contact `chatgpt.com` account usage, directly for a ChatGPT login and through Codex's app-server for an access token; Claude checks contact `api.anthropic.com` OAuth profile and usage endpoints, and only the profile for a setup token; OpenCode Go checks contact `opencode.ai`'s Go usage endpoint. Access tokens authenticate those requests. The plugin does not refresh or rewrite login stores, purchase credits or enable overages. Status/usage checks create no model turns. Tokens and OpenCode's Go key are not saved in jobs, logged or included in the continue prompt; a job keeps only a one-way fingerprint of an automation token. Codex loading a legacy agent-identity token registers an agent task with OpenAI, as the agent's own runs do; each check uses one app-server session for all its requests. The log records that a reservation's extra instructions changed (`note updated` or `note removed`), never their text, and never contains the continue prompt.

Antigravity probes run `agy --version` (up to 15 seconds), then `agy -p /usage --output-format json` (up to 60 seconds, 200 KB output limit) in a disposable temporary directory, with stdin closed. Versions below the conservative 1.1.12 support floor, unparseable versions and 1.1.12 prereleases are not probed. Results, including failures, are cached in memory for 60 seconds after completion per launch: a digest of the executable and the variables that select its data (`HOME`, `USERPROFILE`, `XDG_*`, and `PATH` for a bare command name); concurrent requests share the raw response and map it separately for each model. The digest is not an account identity. Successful replies require `status: SUCCESS`, no model turn and a structured usage command. A turn count other than absent or zero rejects the reply and disables further probes for that launch until plugin restart. The plugin logs only fixed failure reasons, not CLI output or stderr. agy can still create its own log file and update conversation-summary metadata on each probe; the plugin does not remove those files. Windows `.cmd`/`.bat` launchers that cannot safely pass `/usage` use the fallback and log `unsafe_windows_shim`; native executables use the normal probe.

OpenCode opens OpenCode's SQLite database read-only and checks the `session_v2` table for the agent's own session; OpenCode 2 writes that session store, and a database without the session is not its runtime. It then reads the `credential` table for Go or the `session_message` table for free models. It does not run a CLI version check. The selected `opencode-go` key is used only for the Go usage request, which has a 15-second timeout; the key is never saved or logged. These reads and the Go usage call create no model turns. A missing database, table, row or malformed record is logged as a fixed reason, never with its contents.

Continue prompts are sent through Paseo to the existing agent and its provider; the agent can then perform model turns and tools as usual. Local reservation storage does not mean all processing stays on the host.

| Stored data | Location |
| --- | --- |
| Resume jobs, hashed account/model identity (and OpenCode Go credential/model identity), sanitized launch/store selectors, Keychain lookup username, boolean credential-presence flags and one-way automation-token fingerprints, and reservations' extra instructions until they are sent or the reservation ends | `$PASEO_HOME/plugin-data/usage-auto-resume/jobs.json` |
| Recent activity: result and reason, agent ID, provider and the conversation title when recorded, kept for 24 hours | `$PASEO_HOME/plugin-data/usage-auto-resume/history.json` |
| Provider switches | `$PASEO_HOME/plugin-settings/usage-auto-resume/providers.json` |
| Continue prompt (`null` uses the default) and Labs overload switch (default false) | `$PASEO_HOME/plugin-settings/usage-auto-resume/resume.json` |

The default Paseo home is `~/.paseo`. Settings and jobs are separate from plugin source code. A job row this version cannot read is skipped and logged, and is not kept when the file is next written; the other reservations are kept. A file that is not a job list at all is read as empty. `paseo plugin remove` deletes the plugin's `plugin-settings` folder and leaves `plugin-data`, so reservations and recent activity stay until that folder is deleted.

## Troubleshooting

| What you see | Meaning and next step |
| --- | --- |
| No retry after an overload | Check Labs, provider switches, API billing, and whether the final message matches a captured form. Startup scanning does not create overload reservations. |
| Empty Auto Resume list | No eligible stop has been found. Use agents normally; only detected limit stops or enabled overload stops create reservations. Older stops can be outside the startup scan. |
| Waiting for account verification | The CLI authentication could not be confirmed. Check the CLI login and configured launcher. On Windows, the plugin starts npm-installed `.cmd` launchers through `cmd.exe` and reads the login where the CLI reports it, else from the user profile. A launcher path containing `%` or `"` cannot be passed to `cmd.exe` safely, so the check keeps waiting; install the CLI or configure its command at another path. On macOS, check that the daemon's user can access the selected profile's Keychain item or its fallback file and that the login is unexpired. |
| Waiting for usage verification | Usage is unreadable, unrecognized or still exhausted without a usable future reset. The displayed time is the next check; time passing alone does not authorize a continue. |
| Claude setup-token reservation waits for account verification | The token was rejected (revoked or expired), the profile check failed, or after a restart the daemon and provider configuration do not hold the same token. Issue a new token with `claude setup-token`. Once the agent's session opens with it, the reservation made under the old token is canceled as an account change at its next check, and the next limit stop makes a new one. |
| Codex access-token reservation keeps waiting for usage verification | Codex returned no usable rate-limit windows, refused the request, or did not name the workspace and user for the token. Check that `codex login status` accepts the token and that the workspace still allows it. Nothing is sent until Codex reports usable windows. |
| Antigravity follows the notice despite available quota | A stated-reset reservation intentionally skips the initial probe. Before sending, check the daemon log for a fixed unavailable reason, the agy version, the configured launcher and selected model. No account identity is available; unknown models and unsafe Windows shims fall back to the notice. |
| OpenCode waits for verification | Check that OpenCode's database is readable in its data directory and contains the agent's own session. If the log says the session is not in the database, the configured OpenCode server may be on another host or use another data directory. Records older OpenCode wrote without a dedicated free-limit type are not resumed as free. The daemon log gives the fixed reason. |
| Reservation disappeared | It may have been sent, skipped, canceled by agent activity/settings, or reached its retry bound. Open **Recent activity** for the last 24 hours, or check the daemon log. |
| Saved jobs are not checked after restart | Open Auto Resume or let a lifecycle event reconnect the Paseo API. |
| Reservation canceled after changing account or model | Codex and Claude reservations are tied to the original account identity, a Claude setup token's to the token itself, and a Codex access token's to its workspace and user; OpenCode Go reservations to the original credential and key. A subsequent detected limit stop can create a new one. |

Plugin log lines use the `[usage-auto-resume]` prefix in the daemon log.
