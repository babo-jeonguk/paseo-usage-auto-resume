# Paseo 0.15 beta 실행 검증

검증일: 2026-11-03. 대상 Paseo: `0.15.0-beta.1`. 플러그인: `1.3.1`, 커밋 `c63480506a264d171cf625ac7e647f4315512b37`.

## 호환성 판단과 정식 버전 확인 계획

검증한 beta에서는 기존 플러그인을 변경하지 않고 사용할 수 있다. `paseo-plugin.json`의 `requirements.paseo`는 `>=0.11.0`으로 0.15를 허용한다. Paseo의 버전 검사도 prerelease의 기본 버전으로 요구사항 충족 여부를 확인하며, 실제 beta 설치와 실행을 통과했다. 따라서 현재는 실행 코드, manifest, 개발 의존성 또는 플러그인 버전을 변경할 필요가 없다. [Paseo의 버전 검사](https://github.com/getpaseo/paseo/blob/v0.15.0-beta.1/packages/protocol/src/plugin-requirements.ts)

Claude의 정상 종료 후 복구 누락은 Paseo의 재시작 자동 복구와 Claude 실행 연동 쪽 관찰 사항으로, Antigravity의 이전 제한 오류 재전달은 외부 제공자의 기존 동작 문제로 분류한다. 이번 플러그인 수정 대상에서는 제외한다. 정확한 내부 원인을 확정했다는 뜻은 아니며 재현 조건과 증거는 아래에 보존한다. Codex의 테스트용 계정 확인 실패도 Paseo 0.15의 회귀로 분류하지 않는다.

이 문서와 조사 기록을 포함한 브랜치는 Paseo 0.15 정식 버전 확인을 위한 준비용이다. 정식 버전 공개 후 다음을 확인하고, 필요한 변경이 있을 때만 같은 브랜치에 추가한 뒤 메인 병합을 진행한다.

1. 검증한 `0.15.0-beta.1`부터 정식 태그까지 플러그인 인터페이스와 실행 동작의 변경분을 확인한다.
2. 정식 배포본에서 설치, 제한 감지, 재개, 재시작 시 기존 예약 처리와 브라우저의 주요 동작을 다시 검증한다.
3. 외부 문제의 수정 여부와 남은 검증 한계를 갱신한다. 플러그인 변경이 필요 없다면 문서만 반영한다.

현재 결과는 beta에 대한 것이며 정식 버전 검증 완료를 의미하지 않는다.

## 작업 범위와 확정한 동작

이 플러그인은 사용량 제한으로 멈춘 에이전트에 재개 예약을 만들고, 제한이 풀리면 같은 대화에 메시지를 보낸다. Paseo 0.15는 별도로 재시작 전에 실행 중이던 에이전트를 자동으로 이어서 실행한다. 두 기능이 겹칠 때 오래된 예약이 정리되고 중복 메시지가 발생하지 않는지 확인했다.

사용자는 Paseo에서 사용량 조회를 꺼도 플러그인의 기존 동작을 유지하기로 결정했다. 따라서 해당 설정에 맞춰 플러그인을 대기시키자는 이전 제안은 채택하지 않았다. 이번 작업은 실행 검증과 문제 기록에 한정한다. 저장소의 제품 코드, 테스트, 의존성 및 빌드 설정은 수정하지 않는다.

## 실행 환경과 검증의 한계

- Linux, Node `v24.21.0`, Claude Code `2.1.316`, Codex CLI `0.166.0`, Antigravity CLI `1.4.12`.
- npm에 배포된 실제 Paseo `0.15.0-beta.1`을 `/tmp/uar-cli015-verification`에 설치했다. 각 실행에는 별도 저장소 디렉터리와 포트를 사용했다. 사용 중인 Paseo의 대화·설정·플러그인은 변경하지 않았다.
- 실제 Paseo, 실제 제공자 실행 파일, 플러그인 이벤트 처리·예약 저장·30초 주기 자동 재개, Chromium 브라우저를 사용했다.
- 모델 응답은 로컬 서버가 대신 제공했다. 사용량 제한과 정상 응답을 반복 재현했으며 실제 유료 모델을 호출하거나 실제 계정의 한도를 소진하지 않았다.
- 기존 종합 검증 도구는 설치된 테스트용 플러그인 사본에서 계정·사용량 검사만 제어 파일로 대체한다. 따라서 이 실행만으로 실제 계정 인증이나 외부 사용량 서비스 연결을 검증했다고 볼 수 없다. 이 부분은 별도의 기존 CLI 통합 테스트로 확인했다.
- 재시작 추가 검증에서는 로컬 모델 서버가 응답을 지연하여 작업이 실행 중인 상태를 유지했다. 제품 코드에는 지연이나 동작 변경을 넣지 않았다.
- Windows, macOS, 모바일 네이티브 앱, 원격 호스트 및 실제 외부 서비스 연결은 이 실행의 검증 범위 밖이다.

## 사용량 조회를 끈 상태

실제 Paseo 설정 API로 `usage.enabled=false`를 저장한 뒤에도 Claude, Codex, Antigravity에서 사용량 제한 감지, 예약 생성, 수동 재개와 자동 재개가 작동했다. 각 재개 메시지는 한 번씩만 전송됐다. 각 제공자의 확인이 끝나면 설정을 다시 켰다. 계정·사용량 값은 종합 검증의 제어 파일을 사용했다는 한계가 있다.

추가로 `/tmp`에 복사한 기존 CLI 통합 테스트에서 설정 응답에 `usage.enabled=false`를 넣고 실제 Claude CLI를 사용하는 계정·사용량 검사 함수를 실행했다. 조회가 수행되고 정상 구독 상태를 확인하는 검사가 통과했다. 이 경우에도 외부 계정 서비스의 응답은 테스트 데이터이며 실제 사용자 자격증명은 사용하지 않았다.

## 재시작과 남아 있는 예약의 검증 방법

다음 순서를 사용했다. 사용량 제한으로 정상 예약을 만든 뒤 플러그인을 잠시 끄고, 같은 에이전트에 새로운 작업을 시작한다. 그 작업의 응답을 지연시킨 상태에서 플러그인을 다시 켠다. 그러면 플러그인은 작업 시작 이벤트를 놓쳤기 때문에 이전 예약이 남아 있다. 종료 직전 저장 상태가 실행 중인지, 예약 ID가 원래 것인지 확인했다.

이 상태에서 정상 종료 또는 전체 테스트 프로세스의 강제 종료 후 재시작했다. Paseo의 자동 복구 설정을 켜거나 끄고, 일부 실행은 daemon을 종료한 동안 예약 시각도 과거로 이동했다. 모델 서버의 수신 기록, 같은 대화의 사용자 메시지 기록, 예약 파일과 재개 결과 기록을 비교했다. 임의로 예약을 만들어 넣는 대신 플러그인의 정상 예약 생성과 켜기·끄기 기능을 이용했다.

Antigravity의 정상 종료 사례에서 "예약이 남았다"는 검사 실패는 원래 예약이 그대로 남았다는 뜻은 아니었다. 새 메시지로 원래 예약을 취소한 기록과, 그 뒤 새 예약 ID를 확인했다.

새 저장소의 강제 종료 단독 실행에서도 모델 서버의 사용자 메시지를 대조해 Paseo 재개 1개와 플러그인 재개 0개를 확인했다. 결과 기록에는 원래 예약을 `new_message` 사유로 취소한 항목이 있고, 예약 파일에는 복구 메시지 이후 시각을 기준으로 한 새 예약이 있었다. 이 실행은 "예약이 없어야 한다"는 검사에서 실패했지만 중복 전송은 없었다. 증거는 `/tmp/uar-e2e015-agy-crash-results/results.json`과 `/tmp/uar-e2e015-agy-crash-results/observed.json`이다.

예약이 없는 상태의 정상 종료 비교 검사에서도 Codex는 복구 메시지가 도착했고 Claude는 도착하지 않았다. Claude의 문제를 플러그인 예약과의 충돌로 분류하지 않은 근거다.

## 발견한 문제

### 정상 종료 후 Claude 자동 복구 메시지가 도착하지 않은 사례

자동 복구 설정을 켜고 위 순서로 Claude 작업과 오래된 예약을 함께 남긴 뒤 Paseo를 정상 종료하고 재시작했다. 재시작 후 150초 동안 `Resume working.` 메시지가 모델 서버에 도착하지 않아 검증이 실패했다. 같은 제공자의 강제 종료 후 재시작에서는 자동 복구 메시지가 한 번 도착하고, 플러그인은 추가 메시지를 보내지 않은 채 오래된 예약을 취소했다.

정상 종료 시 Claude 로그에는 `ProcessTransport is not ready for writing` 경고가 있었다. 재시작 후 해당 에이전트의 저장 상태는 `closed`, `resumeOnStartup=false`였다. 이 값만으로 복구 의도가 저장되지 않았는지, 소비된 뒤 전송되지 않았는지 단정할 수 없다. 현재까지 확인한 것은 이 조건에서 자동 복구가 완료되지 않았다는 사실이며, 플러그인 때문에 발생했다는 원인은 확정하지 않았다. 코드는 수정하지 않았다.

예약과의 관계를 구분하기 위해 별도 저장소·포트에서 비교 실행했다. 이번에는 플러그인을 끄지 않고 새 작업을 시작하여 이전 예약이 취소된 것을 확인한 다음 정상 종료했다. 종료 직후, 재시작 전 저장 파일에서 이미 `lastStatus=closed`, `resumeOnStartup=false`였다. 재시작 후 45초 동안 자동 복구 메시지가 도착하지 않았다. 따라서 **남아 있는 예약이 없어도 같은 현상이 재현된다.** 원인을 플러그인 예약과의 충돌로 단정할 수 없다. 최초 실행과 비교 실행 모두 로컬 모델 응답을 120초 지연해 작업을 실행 중으로 유지한 조건이다.

비교 증거: `/tmp/uar-e2e015-control.log`, `/tmp/uar-e2e015-control-results/control-claude-shutdown.json`, `/tmp/uar-e2e015-control-results/control-claude-result.json`. 실행 명령은 아래 추가 검증 명령의 스크립트를 `control.mjs`, 제공자를 `claude,codex`, 작업 디렉터리를 `/tmp/uar-e2e015-control`, 결과 디렉터리를 `/tmp/uar-e2e015-control-results`로 바꾼 것이다.

### Codex의 테스트용 구독 계정 확인 실패

기존 명령 `NATIVE_CLI=codex npm run test:native`를 두 번 실행했고, 두 번 모두 테스트용 로그인 계정을 구독 계정으로 확인하는 항목이 실패했다. 기대값은 `auth=subscription`이지만 실제 결과는 `auth=unknown`이었다. 실행 파일 시작과 app server 초기 연결 검사는 통과했다.

이 검사는 Paseo를 실행하지 않고 기존 플러그인의 계정 검사 함수를 직접 호출한다. 따라서 Paseo 0.15로 인해 새로 생긴 문제라고 판단할 근거는 없다. 실제 계정으로 같은 문제가 발생하는지도 확인하지 않았다. 테스트용 자격증명에 대한 Codex의 응답 또는 플러그인의 처리에 추가 확인이 필요하다. 실패를 없애기 위해 검사를 건너뛰거나 코드를 고치지 않았다.

### Antigravity가 정상 응답 뒤 이전 사용량 제한 오류를 다시 기록하고 예약이 생김

수동 및 자동 재개 검증에서 재개 메시지가 모델 서버에 한 번 도착하고 `Done.` 응답도 기록됐지만, 그 뒤 대화에 이전 `Error 429 ... RESOURCE_EXHAUSTED`가 다시 기록됐다. 플러그인은 이를 사용량 제한으로 처리해 새 예약을 만들었다. 원래 예약은 전송됐으나 결과적으로 예약 목록이 비지 않았다. 정상 종료 및 강제 종료 뒤 Paseo의 자동 복구가 실행된 경우에도 원래 예약을 취소한 뒤 새 예약이 생성됐다.

현재 종합 검증 도구는 이 현상을 실패 대신 별도 관찰 결과로 남기고 계속 진행하도록 작성돼 있다. 따라서 전체 실행 결과가 통과여도 "재개 뒤 예약이 모두 정리됐다"고 해석해서는 안 된다. 이 동작이 0.15에서 새로 생긴 것인지는 비교 실행하지 않았다. 기존 검증 코드에도 동일 현상을 다루는 분기가 있어 이번 beta만의 회귀라고 단정하지 않는다. 제품 코드는 수정하지 않았다.

실행 로그의 `NOTE [6/antigravity] row after the continue`에 대화 순서와 새 예약 시각이 기록돼 있다. 원본 [종합 검증 코드](../e2e/e2e.mjs)의 Antigravity 전송 후 예약 확인 부분도 함께 참고한다.

### 기존 종합 검증 도구가 과거 재개 문구를 기다림

저장소의 `e2e/e2e.mjs`는 재개 메시지를 셀 때 `usage limit should now be reset`이라는 이전 문구를 찾는다. 현재 플러그인의 기본 문구는 `Continue the unfinished work from where it stopped.`로 시작한다. 첫 실행에서 실제 재개 메시지가 로컬 모델 서버에 도착했는데도 검증 도구가 인식하지 못하는 것을 확인했다.

저장소의 검증 코드는 수정하지 않았다. `/tmp/uar015-full-harness`에 복사한 검증 도구에서 관찰 문구만 현재 값에 맞춘 뒤 전체 검증을 다시 시작했다. 처음 실행한 두 격리 테스트는 종료했고, 해당 실행의 로그와 파일은 보존했다. 이는 제품의 전송 실패와 구분되는 검증 도구의 불일치다.

추가 재시작 검증에서도 Antigravity는 사용자 지시 뒤 내부 안내 메시지를 추가하므로 "마지막 사용자 메시지에 테스트 문구가 있는가"라는 관찰 조건이 충족되지 않았다. 요청 기록에는 앞선 사용자 메시지에 해당 문구가 들어 있었다. 이 실행은 재시작 검증 전 단계의 제한시간 초과이므로 자동 복구 실패로 집계하지 않았다. `/tmp/uar015-extra-harness/antigravity.mjs`에서 요청에 포함된 사용자 메시지 목록도 확인하도록 관찰 조건을 바꾼 뒤, 아직 검증하지 못한 Antigravity 재시작 사례만 별도 실행했다. 앞서 끝난 Claude/Codex 검증은 반복하지 않았다.

그 연속 실행의 강제 종료 사례에는 `plugin sent a duplicate continuation`이라는 실패도 기록됐다. 그러나 수신 내용의 대화별 식별자와 기록을 대조하니 추가 메시지는 직전 정상 종료 사례의 대화로 전송된 것이었다. 정상 종료 사례에서 재생성된 예약을 검증 스크립트가 과거 시각으로 이동한 영향으로, 현재 강제 종료 사례의 중복 전송으로 집계할 수 없다. 따라서 강제 종료 사례는 새 저장소에서 단독 실행했다.

## 명령과 증거 위치

계정 검사:

```bash
NATIVE_CLI=claude npm run test:native
NATIVE_CLI=codex npm run test:native
```

전체 실행 검증은 기존 `e2e/e2e.mjs`와 동일한 절차를 `/tmp` 사본에서 실행했다. 이전 플러그인 버전 `v1.3.0`을 설치한 뒤 현재 커밋으로 업데이트하고, 검증 후 이전 버전으로 되돌리는 절차를 포함한다.

```bash
node /tmp/uar015-full-harness/e2e.mjs \
  --label linux-0.15.0-beta.1-current-prompt \
  --cli /tmp/uar-cli015-verification/node_modules/@getpaseo/cli \
  --root /tmp/uar-e2e015-full-current \
  --out /tmp/uar-e2e015-full-current-results \
  --suites claude,codex,antigravity \
  --claude /home/babo/.local/bin/claude \
  --codex /home/babo/.local/bin/codex \
  --agy /home/babo/.local/bin/agy \
  --source git:file:///home/babo/Projects/paseo-usage-auto-resume \
  --from v1.3.0 --to c63480506a264d171cf625ac7e647f4315512b37 --ui 1
```

추가 재시작 검증:

```bash
node /tmp/uar015-extra-harness/extra.mjs \
  --label linux-0.15.0-beta.1-restart-current \
  --cli /tmp/uar-cli015-verification/node_modules/@getpaseo/cli \
  --root /tmp/uar-e2e015-restart-current \
  --out /tmp/uar-e2e015-restart-current-results \
  --suites claude,codex,antigravity \
  --claude /home/babo/.local/bin/claude \
  --codex /home/babo/.local/bin/codex \
  --agy /home/babo/.local/bin/agy \
  --source git:file:///home/babo/Projects/paseo-usage-auto-resume \
  --to c63480506a264d171cf625ac7e647f4315512b37
```

실행 로그: `/tmp/uar-e2e015-full-current.log`, `/tmp/uar-e2e015-restart-current.log`. 완료된 종합 검증의 결과 디렉터리에는 `results.json`, daemon 로그, 모델 수신 기록과 브라우저 캡처가 저장된다. 첫 추가 검증은 Antigravity 관찰 조건을 바꾸기 위해 중단했으므로 전체 결과 JSON은 없고, 실행 로그와 완료된 Claude/Codex 사례의 개별 JSON을 근거로 기록했다. CLI 계정 검사 로그는 `/tmp/uar-015-native-claude.log`, `/tmp/uar-015-native-codex.log`, `/tmp/uar-015-native-codex-repeat.log`다. `/tmp` 증거는 이 환경이 정리되면 사라질 수 있으므로 판단에 필요한 결과는 이 문서에도 요약한다.

Antigravity의 관찰 조건을 맞춘 실행은 `/tmp/uar-e2e015-agy-restart.log`에 기록했다. 해당 명령은 추가 검증 명령의 스크립트를 `antigravity.mjs`, 제공자를 `antigravity`, 저장소를 `/tmp/uar-e2e015-agy-restart`, 결과 디렉터리를 `/tmp/uar-e2e015-agy-restart-results`로 지정한 것이다. 강제 종료 단독 실행은 같은 위치의 `antigravity-crash.mjs`를 사용하며 저장소와 결과 경로는 `/tmp/uar-e2e015-agy-crash`, `/tmp/uar-e2e015-agy-crash-results`다.

최종 `npm run check` 로그는 `/tmp/uar-015-final-check.log`다. 결과는 타입 검사 통과, 테스트 536개 통과·실패 0개다. `usage.enabled=false`를 전달한 실제 Claude CLI 검사 로그는 `/tmp/uar-015-native-claude-usage-off.log`이며 2개 통과·4개 조건부 제외다.

## 완료 범위와 남은 확인

이 문서의 기본 호환성 검증, 세 제공자의 사용량 조회 off 동작, 재시작과 기존 예약의 관계 확인을 끝냈다. 발견한 실패와 관찰 도구의 한계는 숨기거나 통과로 바꾸지 않고 위에 구분했다. 코드를 수정하지 않았으며 문서만 추가·갱신했다.

실제 외부 계정·모델 서비스, Windows/macOS/모바일 앱, 네트워크 프록시를 통한 실제 외부 조회, 연결 끊김 전후 동일한 화면의 편집 상태 보존 및 임의의 재시작 시점 전수 검증은 수행하지 않았다. 이번 결과는 검사한 시나리오의 관찰이며 모든 실행 순서에서 정확히 한 번만 재개된다는 보장은 아니다. 특히 Claude 정상 종료 후 자동 복구 누락과 Antigravity의 새 예약 생성은 해결되지 않은 채 기록한 상태다.
