# Paseo 0.15 정식 버전 호환성

검증일: 2026-11-03. 대상: 정식 `0.15.0`. 플러그인: `1.3.1`, 준비 브랜치 `compat/paseo-0.15`의 `13e27c3`(실행 코드는 `c634805`와 동일).

## 결론

정식 0.15에서도 기존 플러그인의 설치·예약·재개·설정·화면·재시작 후 예약 처리를 확인했다. beta 때 내린 **실행 코드·manifest·의존성 변경 불필요** 판단은 이번 결과에서도 유효하다. 이번 브랜치는 조사·호환성 문서만 유지한다.

전체가 문제없이 통과했다는 뜻은 아니다. Antigravity가 이전 제한·과부하 오류를 다시 전달하는 기존 현상은 남아 있으며, 과부하 재시도의 완료·정리 검사는 실제로 실패했다. 외부 문제와 관찰 범위를 아래에 구분한다. 실제 외부 계정·모델 서비스와 네이티브 앱을 검증한 결과는 아니다.

## beta 이후 변경

공식 태그를 비교하면 플러그인·클라이언트·통신 형식 소스는 beta와 동일하다. 제공자 실행과 사용량 조회 구현도 바뀌지 않았다. 서버의 주요 변경은 Paseo 자체의 재시작 자동 복구가 기본 꺼짐으로 바뀐 것이다. 사용량 제한 후 예약을 보내는 플러그인의 자동 재개와 별개다. [정식 릴리스](https://github.com/getpaseo/paseo/releases/tag/v0.15.0) · [태그 비교 조사](research/paseo-0.15-stable-changes.md)

플러그인의 요구 버전 `>=0.11.0`은 정식 0.15를 허용한다. Paseo의 사용량 조회 설정을 꺼도 플러그인의 동작은 유지한다. beta 때 확인한 외부 제공자 문제를 우회하기 위해 플러그인의 처리 규칙을 변경하지 않는다.

## 실행 방법과 자원 관리

실제 Paseo와 Claude Code `2.1.316`, Codex CLI `0.166.0`, Antigravity CLI `1.4.12`를 사용한다. 모델 응답과 계정·사용량 값은 로컬 테스트 데이터로 대체하므로 실제 계정의 인증·외부 모델 서비스 연결을 검증한 결과와는 구분한다. Linux와 Chromium 브라우저가 검증 대상이며 Windows/macOS/모바일 네이티브 앱은 포함하지 않는다.

최초에는 여러 격리 검증을 동시에 실행했으나 서버 메모리 부족과 재부팅이 발생했다. 당시 요청 시간 초과는 제품의 호환성 실패로 집계하지 않는다. 재부팅으로 `/tmp` 실행 환경과 로그도 사라졌다. 재설치를 시도하다가 서버에 이미 설치된 정식 0.15.0을 확인해 중복 설치를 중단하고 해당 실행 파일을 읽어서 사용했다. 검증 저장소와 포트는 별도로 유지했다. 소스 비교 조사 파일은 저장소에 남아 있다.

이후에는 제공자별 검증을 순서대로 실행한다. 검증 프로세스와 자식 프로세스의 RSS 합계가 4 GiB를 넘거나 서버 가용 메모리가 1.5 GiB 미만이면 검증 프로세스만 중단하는 감시 도구를 사용한다. 실행 결과와 최대 메모리를 함께 기록한다. 저장소 코드와 검증 코드는 수정하지 않고 `/tmp`의 검증 도구 사본만 사용한다. 사본은 beta 검증 때와 같이 현재 기본 재개 문구를 관찰하도록 맞췄다.

## 재부팅 전 완료한 별도 검사

- `npm run check`: 타입 검사와 536개 테스트 통과. 실행 결과는 대화에서 확인했으나 재부팅으로 임시 로그는 소실됐다.
- `NATIVE_CLI=claude npm run test:native`: 2개 통과, 4개 조건부 제외.
- `NATIVE_CLI=codex npm run test:native`: 2개 통과, 테스트용 구독 계정 확인 1개 실패, 3개 조건부 제외. beta와 같은 `auth=unknown` 결과다. Paseo를 실행하지 않는 검사이므로 정식 버전의 회귀로 분류하지 않는다.

## 단독 실행으로 확인한 결과

Claude의 기존 종합 검증은 설치·업데이트, 예약·기록 보존, 제한 감지, 시간 변경, 추가 지시, 수동·자동 재개, 예약 끄기, 제공자 끄기, 새 메시지 취소와 대화·설정 화면 등 15개 검사가 통과했다. 기능 검사 실패는 없었으나, 대화를 누적하며 실행하던 중 감시 도구가 RSS 합계 4,138 MiB에서 중단했다. 당시 서버 가용 메모리 최저값은 4,244 MiB였으며 메모리 부족으로 서버가 중단된 것은 아니다. 이 실행 전체를 통과로 표시하지 않고 완료된 검사와 자원 제한 중단을 구분한다.

남은 예약 목록 화면만 새 daemon에서 분리 실행했다. 날짜별 분류, 한 예약의 시간·추가 지시만 변경, 해당 대화 열기, 전체 예약 켜기·끄기, 꺼진 예약의 건너뛰기와 지시 삭제, 최근 활동의 건너뛴 결과 표시가 통과했다. 이 화면 실행은 두 대화만 만들었으며 최대 RSS 합계 2,901 MiB, 서버 가용 메모리 최저값 3,213 MiB였다. 새 저장소의 최근 활동은 실제로 발생시킨 건너뛰기 결과만 확인했으며, 모든 결과 종류를 재현했다고 주장하지 않는다.

첫 실행의 로그는 `/tmp/uar015-stable-claude.log`, 자원 기록은 `/tmp/uar015-stable-claude-resources.json`이다. 분리 화면 실행의 결과·이미지는 `/tmp/uar015-stable-screen-results`, 자원 기록은 `/tmp/uar015-stable-screen-resources.json`에 있다. 임시 파일은 다음 재부팅이나 환경 정리 때 사라질 수 있어 핵심 결과를 이 문서에도 보존한다.

Codex와 Antigravity는 각각 새 daemon에서 기본 종합 검증을 실행했고 각 10개 검사 통과, 검사 실패 0개로 종료했다. 두 실행 모두 Paseo의 사용량 조회를 꺼 두고(`usage.enabled=false`), 정식 버전에서 별도 설정이 없는 재시작 자동 복구가 꺼져 있음을 확인했다. 제한 감지, 수동·자동 재개, 제공자 끄기, 놓친 제한의 재발견, 재시작 후 닫힌 대화 재개, 기록 조회와 이전 플러그인으로 되돌리기를 확인했다.

다만 Antigravity의 수동 및 자동 재개 뒤 이전 제한 오류가 다시 전달되어 새 예약이 생기는 현상은 각 한 번씩 관찰됐다. 기존 검증 도구는 이를 별도 관찰로 남기므로 검사 실패 0개가 이 현상이 해결됐다는 뜻은 아니다. beta와 같은 외부 문제로 기록하며 플러그인 규칙은 변경하지 않는다.

Codex 실행의 최대 RSS 합계는 1,783 MiB, 서버 가용 메모리 최저값은 4,138 MiB였다. Antigravity는 각각 1,258 MiB와 4,173 MiB였다. 두 실행의 결과는 `/tmp/uar015-stable-codex-results`, `/tmp/uar015-stable-antigravity-results`에, 자원 기록은 같은 이름의 `-resources.json` 파일에 있다.

## 나머지 재시작 검사와 과부하 재시도

Claude의 놓친 제한 재발견, 재시작 후 닫힌 대화의 예약 재개, 이전 플러그인 버전으로 되돌린 뒤 기록 보존은 새 daemon에서 3개 모두 통과했다. Paseo 자체의 복구가 기본으로 꺼진 상태에서도 플러그인의 예약 재개는 한 번 실행됐다. 결과는 `/tmp/uar015-stable-lifecycle-results`에 있다.

설정에서 켜는 일시적 과부하 재시도 기능도 제공자별로 새 daemon에서 검증했다.

| 제공자 | 결과 |
|---|---|
| Claude | 기능을 끄면 예약하지 않음, 켜면 예약·전용 재개 문구·추가 지시 전송과 완료 후 정리, 다시 끄면 즉시 취소: 3개 통과 |
| Codex | 같은 3개 검사 통과 |
| Antigravity | 끄기 상태의 예약 방지와 설정 변경 시 즉시 취소: 2개 통과. 재개 후 완료·정리: 1개 실패 |

Antigravity의 실패 사례에서는 예약이 생성됐고 전용 문구와 추가 지시가 전송되는 검사도 통과했으나, 정상 완료 대신 이전 오류가 다시 전달되어 `failed`로 끝났다. 검증 코드는 이를 숨기지 않고 `completed` 기대값 불일치로 실패 처리했다. beta에서 분류한 외부 오류 재전달 현상과 같은 종류로 기록하고 플러그인의 감지 규칙을 바꾸지 않는다. 결과·대화 기록은 `/tmp/uar015-stable-overload-claude-results`, `/tmp/uar015-stable-overload-codex-results`, `/tmp/uar015-stable-overload-antigravity-results`에 있다.

## 실행 요약과 재현 방법

| 실행 | 완료한 검사 | 최대 RSS 합계(MiB) | 서버 가용 메모리 최저(MiB) |
|---|---|---:|---:|
| Claude 기존 종합 검증 | 15개 통과 후 자원 제한 중단 | 4,138 | 4,244 |
| 예약 목록 화면만 분리 | 6개 통과 | 2,901 | 3,213 |
| Codex 기본 기능 | 10개 통과 | 1,783 | 4,138 |
| Antigravity 기본 기능 | 10개 통과, 예약 재생성 별도 관찰 2건 | 1,258 | 4,173 |
| Claude 남은 재시작·기록 검사 | 3개 통과 | 1,431 | 4,538 |
| Claude 과부하 재시도 | 3개 통과 | 1,524 | 5,352 |
| Codex 과부하 재시도 | 3개 통과 | 1,547 | 4,926 |
| Antigravity 과부하 재시도 | 2개 통과, 1개 실패 | 1,217 | 4,938 |

분리 이후에는 동시에 하나의 검증 daemon만 실행했다. 모두 종료된 다음에 다음 실행을 시작했으며, 추가 자원 제한 중단이나 서버 메모리 부족은 발생하지 않았다. RSS 합계는 검증 도구·daemon·제공자 실행 파일·브라우저 등 자식 프로세스 전체의 합계로, 플러그인 하나의 메모리 사용량을 뜻하지 않는다.

검증 도구는 기존 `e2e/e2e.mjs`, `e2e/ui-steps.mjs`, `e2e/overload.mjs`의 절차를 사용했다. `/tmp/uar015-stable-harness` 사본에서 현재 재개 문구를 관찰하도록 맞추고, 자원 제한 뒤 미완료 검사만 분리했다. 화면의 최근 활동 검사는 새 환경에서 실제 발생한 건너뛰기 결과만 기대하도록 범위를 줄였다. Codex·Antigravity의 기본 기능 실행은 초기 설정에 사용량 조회 꺼짐을 추가했다. 저장소의 검증 파일은 수정하지 않았다.

명령의 공통 인수는 다음과 같다. 실행별로 `--suites`, `--root`, `--out`, `--label`을 달리했다.

```bash
--cli /home/babo/.nvm/versions/node/v24.21.0/lib/node_modules/@getpaseo/cli
--source git:file:///home/babo/Projects/paseo-usage-auto-resume
--from v1.3.0 --to 13e27c38f929653b330f71150978db32ad1e5f29
```

실행 파일은 `e2e.mjs`(첫 Claude 실행), `screen-only.mjs`를 호출하는 `focused.mjs --task screen`(화면만), `usage-off.mjs`(Codex·Antigravity 기본 기능), `focused.mjs --task lifecycle`(Claude의 나머지 검사)다. 과부하 검사는 원본 `node e2e/e2e.mjs --overload 1`을 사용했다. 과부하 검사는 현재 저장소의 소스를 임시 디렉터리에 복사해 설치하며 Git 버전 인수는 쓰지 않는다. 모델 API와 계정·사용량 조회만 기존 테스트 방식으로 대체하고 나머지는 실제 코드다.

메모리 감시는 `/tmp/uar015-stable-harness/guard.py`, 나머지 실행의 순차 진행은 `/tmp/uar015-stable-harness/rest.sh`로 수행했다. `/tmp/uar015-stable-<실행 이름>.log`와 `-resources.json`에 결과가 기록된다. 이 임시 도구와 로그는 영구 보존되는 검증 기반이 아니므로, 재현할 때 위에 설명한 사본 변경과 분리 조건을 적용해야 한다.

## 남은 범위

실제 유료 모델·외부 계정 서비스, Windows/macOS/모바일 네이티브 앱, 실제 프록시 연결과 연결 끊김 전후 편집 상태 보존은 이번 실행에 포함하지 않았다. Paseo의 복구 설정을 명시적으로 켠 뒤의 실행 중 충돌 사례와 Claude의 정상 종료 후 복구 누락은 정식 버전에서 다시 재현하지 않았다. 해당 구현은 beta와 동일하지만 소스 동일성을 실제 재실행으로 표현하지 않는다. 기본 복구 꺼짐 상태의 닫힌 대화 예약 재개는 세 제공자에서 직접 확인했다.
